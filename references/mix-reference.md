# 混排引用

混排处理等级与普通处理等级/优先级是独立配置对象。

## 规则

1. 先读取垂类详情，确认是否存在 `混排处理等级`。
2. 开混排垂类新增或复制优先级后，必须把优先级 ID 加入对应混排。
3. 混排顺序按需求或来源优先级相对位置处理，不能只检查是否存在。
4. 未开混排垂类不新建混排。
5. 判断开混排时优先使用“垂类 + 优先级名称”；未开混排时使用“垂类 + 处理等级名称 + 优先级”。
6. 只有 Base/日统计而没有 DMP 垂类记录时，标记“待判断”，不能强行推断。

## 写后断言

- 目标优先级 ID 在正确混排处理等级中存在。
- 混排引用的优先级名称和源处理等级 ID 正确。
- 相邻优先级顺序未被无关调整。
- 未开混排垂类没有新增混排对象。

## 专用保存契约与读写转换

普通等级保存后，后台可能自动删除已移除优先级的混排引用、更新来源名称，但不自动补齐新增引用或重排。先重新读取，再对明确的差异计算补丁，不能假定混排完全不变，也不能将这些联动作为任意变化的豁免。

已核实的 `dealLevelVerticalEdit` 混排保存请求使用 `list_detail_id`、`action: 1`、`update_tab: 3` 和 `mix_deal_level_data`（完整混排等级数组）。不能调用只生成 `deal_level_data` 的普通 `saveLevel` 并仅修改 `update_tab`；错误字段可能清空全部混排等级。通用条件脚本不支持混排写入。

读取表示与写入表示不同。当前核实的前端契约中，引用的 `name` 写入来源优先级名称，`priority_name_show` 写入来源展示名称；读取时后台把 `name` 重算为混排 P 编号，并返回 `source_priority_name` 和 `source_priority_name_show`。基于读取对象构造写入对象时，逐条转换为：

```js
ref.name = ref.source_priority_name;
ref.priority_name_show = ref.source_priority_name_show || '';
```

不能将混排 P 编号原样回写为来源名称。使用前须核对当前前端/接口契约及来源优先级；来源字段缺失时停止，不能用空值代替未知名称。上述空字符串只适用于已核实允许空值的来源展示名。

保存前保留完整混排快照；提交前重新读取并检查并发变化。完整数组必须保留所有非目标等级、引用顺序和处理人，禁止仅传一个修改等级。请求成功后重新读取全部混排，逐项核对等级 ID、来源等级 ID、优先级 ID、两种来源名称、成员、顺序、处理人及开启状态。引用总数只是辅助检查，不能替代字段比对；服务器重建产生的创建人变化须单独报告，不能忽略为普通元数据。

验收失败立即停止后续写入，保留前后证据；依据快照和当前契约制定恢复方案，不盲目重放失败请求。配置回读通过与实际任务分发/打标效果分别汇报，未验证的业务影响保留待验证状态。
